# 网页性能与运行健康记录

## 2.5.45 修复

- 每次连接稳定约 30 秒后，使用 SDK 后台任务向本地网关发送四个 1,024 字节探测包；一轮完成后等待 30 秒再检测，不访问公网。主循环不等待 Ping，串口和 HomeSpan 仍正常调度。
- 每轮收到少于三个回复记为异常。连续三轮异常且本次连接已持续至少 90 秒，才请求断开并通过 HomeSpan 重新扫描、连接 Wi-Fi。没有自动重启整块 ESP32。
- 如果网关从未正常响应过探测，必须同时出现至少三次网页发送超时才允许触发恢复，避免仅因路由器屏蔽 ICMP 而反复重连。
- 恢复重试冷却依次为 5、10、20、30 分钟，持续健康十分钟后重置。上传固件和已安排重启期间暂停恢复操作。
- 状态接口增加 `wifiHealth`：当前/上次 AP、信道、实际省电状态、探测结果、恢复尝试次数、断线原因，以及最近恢复前的 AP、信道和信号。连接和恢复日志写入原有环形日志。
- 重连后只重新启动 HTTP 监听，不重复分配路由处理器，避免恢复动作自身引入内存增长。当前 Wi-Fi 省电配置和发射功率保持原有设置。
- CSS/JavaScript 改为主循环每次最多发送 1,024 字节，允许短暂 TCP 停顿；连续十秒无发送进展或总传输达到六十秒才放弃。不再在一个资源处理函数中持续等待全部内容写完。
- 页面脚本下载失败会重试，最多三次；长时间下载和启动失败都有明确提示。固件版本变化使浏览器使用新的资源 URL。

主机回归已覆盖恢复阈值、ICMP 不应答、冷却/退避重置、上传暂停条件、32 位计时溢出、HTTP 停顿和部分写入，以及实际 CSS/脚本加载重试和原有独立日志窗口行为。ESP32-S3 编译通过，OTA 镜像为 1,845,632 字节；镜像头、分区容量、SHA-256 及最终构建输入一致性检查通过。自动恢复仍需刷入后进行实机及长期验证，不能据此声称已经证明最初 Wi-Fi 状态恶化的底层原因。

## 2.5.44 网页卡顿的重启前后对照（2026-10-25）

用户报告运行数天后网页先缺少样式，随后样式出现但仍停留在“连接中”，全部状态为空；另一台手机访问也同样慢。以下为同一固件重启前后的实测，诊断未修改空调状态和设备配置。

| 项目 | 故障时 | 用户重启 ESP32 后 |
| --- | --- | --- |
| 运行时间 | 242,746 秒，约 2 天 19 小时 | 48–54 秒 |
| Wi-Fi RSSI | −69 至 −67 dBm | −55 至 −52 dBm |
| 1,024 字节 Ping | 10 次收到 2 次，丢失 8 次 | 10 次全部收到 |
| CPU 抽样负载 | 约 2.2%–2.4% | 约 0.75%–2.5% |
| 内部 RAM 可用 / 最大连续块 | 约 74 KB / 57,332 字节 | 约 74 KB / 57,332 字节 |
| 状态接口六次平均耗时 | 1,120.2 ms | 203.3 ms |
| CSS 完整性 | 声明 9,975 字节；一次仅收到 8,816 字节即结束，耗时 16.31 秒 | 9,975 字节完整，221.2 ms，与源码一致 |
| JavaScript 完整性 | 声明 29,696 字节；一次仅收到 2,048 字节后读取超时 | 29,696 字节完整，804.0 ms，与源码一致 |
| 网页发送超时累计 | 诊断期间从 13 增至 20 | 复测结束为 0 |

同一台电脑到路由器的对照：32 字节 Ping 12 次全部收到、0–2 ms；1,024 字节 Ping 4 次全部收到、均小于 1 ms。电脑路由表显示目标网段通过本地以太网接口直连。

证据能确定的故障链：ESP32 侧网络传输出现丢包和停滞，网页响应不完整；`ResponsiveWebServer::writeCooperatively()` 在连续 2 秒没有发送进展时关闭连接，会进一步截断响应。浏览器未成功加载 JavaScript 后，页面保持 HTML 中的“连接中”和空白数据。CPU、内部堆和最大连续块的对照未见内存耗尽的证据。

用户随后确认：只重启了 ESP32，板子和天线位置未改变，路由器未重启。重启同时恢复了信号读数和传输，但尚不能由此确认是 AP 关联变化、无线环境还是 Wi-Fi 驱动/省电状态导致。故障前的 BSSID、信道和实际省电状态未被当前接口记录，因而不能追溯重启前后是否连接同一 AP。未将本次故障归因于登录过期或静态资源体积，也未因此修改固件。

源码核对：HomeSpan 接管 Wi-Fi 重连（关闭 Arduino 自动重连），在连接时扫描所有信道并按信号选择同名 AP；当前项目没有启用其周期重扫功能。现有逻辑可处理断线重连，但没有检测“仍报告连接、实际严重丢包”的网络健康恢复逻辑。因此不能依靠 `WL_CONNECTED` 判定链路正常。这个缺口能解释故障为何持续到人工重启，但不能代替对最初链路恶化原因的证明。

## 找到的响应瓶颈

旧版每次切换页面都会重新下载内嵌的约 38 KB 公共 CSS 和 JavaScript，HTML 使用 `no-store`，公共资源无法跨页面复用。接口本身通常较快，页面完整传输显著更慢。

另有两个独立的刷新周期：旧版浏览器每 2 秒读取缓存状态，固件每 5 秒自动查询空调。读取接口耗时与空调物理状态的更新间隔需要分别看待。

## 2.5.43 改动

- 公共资源改为同一 ESP32 下的 `/assets/app.css?v=2.5.43` 和 `/assets/app.js?v=2.5.43`，资源仍保存在固件 Flash；不使用 CDN、互联网或其他服务器。
- 登录后本地静态资源允许浏览器私有缓存，并提供 ETag 条件请求。固件版本变化时资源 URL 改变，避免沿用旧版脚本。
- HTML 和状态、指标接口保持不缓存。静态资源缓存后，五个页面 HTML 大小为 3,386–7,027 字节，比旧版减少约 84%–92%；这是源码体积计算，实际耗时仍需刷入测量。
- 浏览器状态刷新周期改为 1 秒；指标和日志周期、美的串口自动查询周期不变。
- 缓存不会改变空调状态确认逻辑，也不会伪造回报；未调整 Wi-Fi 省电、发射功率、串口协议或 HomeKit 调度。

已完成脚本语法检查、原有日志窗口主机回归检查和 ESP32-S3 固件编译。新固件的浏览器缓存命中、实际耗时和长期资源趋势仍需刷入验证。
